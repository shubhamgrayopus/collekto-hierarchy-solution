Godrej

Hierarchy solution — how it works

Move from the per-manager agency interim model, configure who sees which cases, how teams and sub-tenants appear in dropdowns, how allocation works, and how we roll out phase by phase.

Tenant: Godrej Identity: Database profiles Branch: Optional / future-ready Apps: Web · Manager · Field

Key flows

1. Three layers

Identity = who you are. Authorization = what you may do. Visibility = which loans appear.

ACCESS = Identity + Permission + Matching Visibility

2. Today vs target

Today: agency per manager → portfolios multiply. Target: Visibility (team + Command Tower rules) — no agency-per-manager for access.

3. Command Tower rules vs team rules

Command Tower rules = Product/Bucket/Agency on the loan (from CT map). Team rules = Assigned Users / Self. Same user can have both (OR).

4. How a loan becomes visible after allocation

Assign the worker only (TC/FA). Managers/ACMs see via Visibility — not dual assignees on the loan. LMS = loan details only; Agency defaults to Inhouse.

5. Who appears in dropdowns

Manager = Assigned Users only. Sub-tenant = Command Tower scope + people resolver (+ direct Assigned Users if no manager).

7. Publish configuration

1. Executive summary

Godrej needs a clear collection hierarchy. Today an interim model creates a separate agency for each manager, so portfolios multiply as managers × product/bucket.

To solve this hierarchy issue for Godrej, we implement Identity, Authorization, and Visibility so the per-manager agency pattern is no longer required for access control.

Identity

Who are you?

Profiles and sessions in the database.

Authorization

What can you do?

Role → permissions.

Visibility

Which cases?

Command Tower rules + team rules + Self / All Cases.

ACCESS = Authenticated Identity + Required Permission + Matching Visibility

2. Problem statement

2.1 Intended Godrej hierarchy (business)

flowchart TB TA[Tenant Admin] CM[Collection managers / Command Tower scope] M[Manager] TC[Telecaller] FA[Field Agent] Loans[Loans / Cases] TA --> CM --> M M --> TC M --> FA TC --> Loans FA --> Loans

Business needs include: manager sees their team’s cases; telecaller/field agent see assigned cases; admins see wider Command Tower scope; mixed product/bucket under one manager without inventing fake agencies.

2.2 Current interim model

Temporary solution: a separate agency is created for each manager so that manager’s telecallers and field agents (and portfolios) sit under that agency.
MechanismEffect
One agency per managerIsolates each manager’s team
Portfolio = Agency × Product × BucketSame product/bucket repeated under every manager agency
Net resultManagers × portfolios to create and maintain
Command Tower / CM filtersOften used alongside this to filter by Command Tower rules on web/reporting

2.3 What breaks or becomes hard

  • Onboarding a manager means agency + many portfolios + people membership
  • Moving a telecaller/field agent means portfolio/agency maintenance
  • Dashboards, loan lists, reports, and mobile apps all inherit the same structure
  • LMS loan ingest (replacing import) must not recreate the same agency explosion
  • No clean model for “this manager sees T1, T2, F1” without agency isolation

3. Solution architecture

Visibility is configured case scope, not “simulate hierarchy with agencies.” Hierarchy-like outcomes (manager team, Command Tower scope, admin all-cases) are expressed as rules.

3.3 What this deliberately separates

Visibility (this solution)

Which loans appear on lists, dashboards, reports, mobile home screens.

Worker assignment

Who is allocated to work a loan (TC/FA). After assign, SELF visibility applies.

Agency allocation

Which agency owns the loan. Default Inhouse. New page for future external agencies — not driven by LMS.

LMS boundary: LMS sends loan details only (product, bucket, balances, customer fields, etc.). It does not allocate agency. Agency is set in Collekto: Inhouse by default; when Godrej later onboards an external agency, ops use the Agency Allocation page to move loans to that agency. Today’s multi-agency setup exists only because of the per-manager agency interim model — that goes away with Visibility.

2

3

Default automation (recommended): on create of Telecaller / Field Agent, system auto-adds Self Assigned = Yes into a draft visibility set (still published with audit). Manager team links are maintained via Assigned Users on the manager’s rules.
Managers who allocate: Assigned Users alone only shows loans already assigned to that manager’s TC/FA. Unassigned loans have no assignee, so they never match Assigned Users. A manager who needs to pick up and allocate unassigned loans must also have Product + Bucket (and typically Agency = Inhouse) Command Tower rule rows — otherwise they cannot see those loans to assign them. Assigned Users-only is enough only for managers who only supervise already-assigned team work.

5A. Who appears in dropdowns — Managers vs Sub-tenant roles

There are two related but different questions:

Case visibility

Which loans/cases appear on lists, dashboards, and reports.

People visibility (dropdowns)

Which managers / telecallers / field agents appear when a user opens a filter or assignment dropdown.

Both are driven by configuration — not by creating a separate agency per manager. Case visibility uses Visibility rules. People dropdowns use the team roster derived from those rules and, for sub-tenant roles, from Command Tower rules.

5A.1 Manager — only assigned telecallers & field agents

Rule: A manager’s TC/FA dropdowns show only the users listed in that manager’s Visibility Assigned Users configuration — not every telecaller/field agent in the tenant.

How it is configured

F1 Y F1 sees only self-assigned cases

What the manager sees where

Field Agent dropdown Only F1, F2
Loan list / Manager App team loans Assigned team work: assignee ∈ {T1, T2, F1, F2}.
Unassigned pool (to allocate): only if M1 also has Product+Bucket (+ Agency) Command Tower rows — Assigned Users alone cannot surface unassigned loans.

How the roster is loaded at runtime

1
Manager logs in → Identity resolves profile M1.
2
System loads M1’s active Visibility rules and reads Assigned Users.
3
Roster API returns only those profile ids, split by role (Telecaller vs Field Agent).
4
UI dropdowns bind to that roster. No portfolio membership and no “all users in my agency” query.

Adding or removing someone from a manager’s team

  • Add: put the TC/FA id into M1’s Assigned Users → publish Visibility → dropdown and case scope update together.
  • Remove: delete id from Assigned Users → publish → they disappear from M1’s dropdowns and from M1’s assignee-based case scope.
  • TC/FA keep Self visibility for their own cases regardless of which manager lists them.
Multi-manager teams: If both M1 and M2 must supervise the same people, list the same TC/FA ids on both managers’ Assigned Users rows. That replaces sharing one agency.

Direct report to ACM / RCM (no manager in between)

Yes — this is supported. Assigned Users is not limited to the Manager role. A telecaller or field agent can report directly to an ACM or RCM (or ZCM/NCM) without a manager profile.

  • Solved: no need to invent a dummy manager or a per-manager agency just to hang TC/FA under ACM/RCM.
  • Mixed teams: same ACM can have some people via managers (CT scope → manager → Assigned Users) and some via direct Assigned Users on the ACM.

5A.2 Sub-tenant roles (NCM / ZCM / RCM / ACM) — dropdowns & Command Tower

Sub-tenant users are Tenant Admin–class profiles with a Command Tower scope (often aligned to NCM → ZCM → RCM → ACM). They need dropdowns for child CMs, managers, telecallers, and field agents that sit under their Command Tower scope — not the entire tenant directory.

What Command Tower contributes

Command Tower stores the org map, for example:

NCM → ZCM → RCM → ACM → Agency → Product → Bucket

For a logged-in sub-tenant user, Command Tower answers: “Which agencies / products / buckets (and child CM ids) sit under my node?”

How dropdown population works by sub-role

Logged-in sub-role Command Tower scope Dropdowns they see
NCM All ZCMs (and below) under this NCM in CT ZCM list from CT;
RCM / ACM cascaded from selected ZCM;

ZCM RCMs under this ZCM RCM → ACM cascade; Managers / TC / FA under that subtree only
RCM ACMs under this RCM ACM list; Managers / TC / FA under those ACMs’ agencies / Command Tower scope
ACM Agencies (and product/bucket) under this ACM Managers / TC / FA linked to those agencies or to managers in that Command Tower scope — not tenant-wide
Primary Tenant Admin (no sub-role) Full CT optional for filters Can load full NCM→… cascade and wider people search (still subject to All Cases for loans)
flowchart TB ST[Sub-tenant user e.g. ZCM] CT[Command Tower map] Scope[Resolve subtree: RCM ACM Agency Product Bucket] People[People resolver] DD[Dropdown options: child CMs Managers TC FA] Cases[Case Visibility rules for this user] ST --> CT --> Scope Scope --> People --> DD ST --> Cases

Two-step resolve (important)

1
Scope from Command Tower: from the logged-in CM id, read CT to get child CM ids + Agency (+ Product/Bucket) set for that subtree.
2
People from profiles: return Managers / Telecallers / Field Agents in that Command Tower scope — (a) managers under the CT agencies, (b) TC/FA on those managers’ Assigned Users, and (c) TC/FA listed directly on the logged-in CM’s Assigned Users (no manager required).
3
Cases from Visibility: loan lists for the sub-tenant still use their published Visibility rules (often Agency/Product/Bucket Command Tower rules seeded from the same CT map). Selecting a person in a dropdown only narrows further; it cannot expand beyond Visibility.

Cascade behaviour in UI (multi-select)

  • NCM selects one or more ZCMs → RCM options reload from CT under those ZCMs
  • RCM selection → ACM options reload
  • ACM / agency selection → Manager and TC/FA dropdowns reload from the people resolver
  • All cascades are scoped to the logged-in sub-tenant’s CT subtree (they never see another NCM’s tree)

7. How Command Tower is taken into account

Position: Command Tower remains Godrej’s organisational / mapping artefact (NCM → ZCM → RCM → ACM → Agency → Product → Bucket). It is not the runtime security engine. Visibility rules are the runtime security engine.

7.1 Roles of the two systems

Command Tower

  • Org / Command Tower map
  • Useful for reporting drill-downs and ops reference
  • Can inform what Product/Bucket/Agency belong to a CM Command Tower scope
  • May continue to be uploaded/maintained as today for reporting

Visibility Service

  • Authoritative for “which cases can this user access?”
  • Enforced on CRM, Manager App, Field App APIs
  • Configured via Excel / Admin publish
  • Fail closed; versioned; cached

7.2 How CT feeds the hierarchy solution

1
Discovery: Export current Command Tower mappings (CM → agencies → products/buckets).
2
Seed: Generate Visibility workbook rows for CM/manager users from CT (Agency / Product / Bucket sets).
3
Team rules: Add Manager Assigned Users from current manager↔TC/FA relationships (not from CT alone).
4
Cut over: Loan/dashboard/report APIs enforce Visibility. CT filters on UI become optional convenience only.
5
Steady state: Day-2 access changes go through Visibility publish. CT updates for org analytics can continue in parallel without granting access by themselves.

7.3 Command Tower and people dropdowns (sub-tenant)

For sub-tenant roles, Command Tower is the directory scope for cascading filters and for deciding which managers / telecallers / field agents appear in dropdowns (see §5A). Visibility remains the case scope.

7.4 What we will not do

  • Will not make Command Tower the sole ACL for case lists
  • Will not require CT sync on every page load for security of loan rows
  • Will not block hierarchy go-live on rebuilding CT as a full hierarchy engine
  • Will not show tenant-wide TC/FA lists to managers or to sub-tenants outside their Command Tower scope

If Godrej later wants automatic sync “CT change → Visibility draft,” that can be a later phase (integration), after the Visibility engine is live.

8. Branch dimension — non-mandatory for Godrej now

Godrej does not operate a branching model in Collekto today. The Visibility model still includes Branch as a first-class dimension in the workbook and data model so it can be enabled later without redesign.

11. Phase-wise rollout into the system

Rollout is incremental so Godrej keeps operating while the interim agency model is retired.

Phase 0 — Align & inventory Prep

  • Confirm roles, sample manager teams, product/bucket masters
  • Inventory Command Tower usage vs portfolio/agency interim model
  • Inventory APIs: loan list, dashboard, reports, mobile, settlement, integrations
  • Agree Branch remains optional / unused at go-live

Phase 1 — Visibility foundation Build

  • Visibility schema, resolver, cache, versioning, fail closed
  • Excel upload → validate → preview → publish
  • Visibility Admin screens in CRM
  • Branch column present but non-mandatory

Phase 2 — Seed from current Godrej reality Migrate

  • Generate workbook from: Self for TC/FA, Assigned Users for managers, Product+Bucket for managers who allocate, All Cases for primary admin
  • Enrich CM/manager Command Tower rules from Command Tower Product/Bucket/Agency maps where applicable
  • Dry-run publish; reconcile sample user case counts vs old behaviour

Phase 3 — Enforce on operational CRM Cutover

  • Loan pages (list + detail), search/filters (multi-select ∩ visibility)
  • Dashboards aggregates
  • Assignment remains separate but only on visible loans
  • Settlement list/approve scoped via loan visibility

Phase 4 — Mobile apps Apps

  • Shared mobile APIs rewired to Visibility
  • Field Agent Android + iOS: SELF; portfolio access demoted
  • Manager Android + iOS: Assigned Users / dimension rules
  • Coordinated app release with backend

Phase 5 — Reports, jobs, integrations hardening Harden

  • MIS/report row security on Visibility
  • Batch jobs that assume per-manager agency reviewed
  • SMS / Payment / LMS posting: loan-id based; remove brittle portfolio assumptions
  • LMS ingest: loan details only; Agency = Inhouse default; no per-manager agency side effects
  • Agency Allocation page: ship for future external-agency moves (steady state = Inhouse)

Phase 6 — Retire interim hierarchy model Retire

  • Stop creating agencies per manager for access
  • Collapse to Inhouse as the default agency; use Agency Allocation only when external agencies exist
  • Command Tower remains optional for org/reporting only
  • Document steady-state onboarding SOP for Godrej ops
Parallel run: Phases 2–3 may briefly compare old vs new counts. Security authority switches to Visibility at the agreed cutover; interim agency model is then frozen for access.
